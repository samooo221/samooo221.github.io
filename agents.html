I direct AI agents,
and I adapt
as they get better.

For 107 days I worked with AI coding agents, almost every day. I did not build the gates, guards and tests myself: I asked the agents to check their own work, and with every better model version they did more of it on their own. My part was to notice each change and adapt my workflow to it. This page is the result of a large-scale audit of my entire work with AI agents. I made it by deploying a large agent workflow across my whole portfolio, on GitHub and on my computer.

Checks that can fail 01–06

01A check that never failed gives no proof that it tests anything.

A check is not a guard until I have watched it fail

Problem
If a check has never failed, I cannot tell whether it tests anything. It prints OK, and everyone trusts it.
What I did
From 25 Jul, a worker had to revert its own change and see its check go red. If the check stayed green, the job went back. I had agents break the guards on purpose and then audit that sweep too. Gates were fed known-bad input. A gate that did not run must never print OK.
Result
In one session, agents broke 16 guards on purpose, and 2 of them did not notice. The sweep itself once scored 100% while testing nothing; I had that fixed as well. The same habit shows up in five projects, July to October.
Limit
The counts come from project notes and git history. I did not re-run the test suites for this page.

02A worker's finding can sound right and still be wrong.

A second stage whose only job is to refute

Problem
Workers report findings with confidence. Some are wrong, and acting on a wrong one wastes a day.
What I did
After the workers report, a verifier tries to break each claim before anyone acts. It re-opens every cited file, re-runs the gate or argues the opposite. Findings use fixed formats. Every report ends with a list of what was not checked.
Result
In a 35-seat review panel on my game project, 203 findings came in. 196 held up, 6 were refuted and 1 stayed unclear. In a later review of my own portfolio, the checks overruled the first report 11 times.
Limit
The panel numbers are model-made. A model verifier is not a human reviewer.

03A model reviewing its own family's work tends to agree with it.

A reviewer from another model family, by rule

Problem
Two sessions of the same model family tend to agree with each other. That is not a review.
What I did
On 7 Aug I deleted a working reviewer because it came from the writer's model family and kept agreeing. My rule since then: the reviewer never comes from the writer's family. Codex reviews Claude, and other families review the rest. I measured the effect and made the rule part of every project.
Result
Two reviewers from different families read the same 11-file snapshot. They shared only 1 of 11 findings. Once, four same-family sessions approved a file, and an outside model found its fault in about 10 minutes. From 19 Sep to 8 Oct I ran 441 Codex sessions.
Limit
Both figures come from my own project notes. A model reviewer is still not a human reviewer.
Evidence
review reportsproject notesnot re-run
04A model judge can give two verdicts on the same answer.

Measure the judge before I trust the score

Problem
Model judges decide what counts as better. If the judge is noisy, every score is noise too.
What I did
I tested my own graders. I gave them byte-identical answers and counted how often the verdict changed. A model judge never decides alone: it proposes, and a measuring tool is the gate. Where I could, I scored with no model at all.
Result
Byte-identical answers got different verdicts on 2 of 18 rows, about 11%. So one judge could not show an effect smaller than 3 rows. I hired a new judge only after a gold-set test: 75% agreement and 0 wrong agreements in 32 trials.
Limit
The legal assistant I measured this on missed its own target: 43% defensible answers against 75 to 80%. That repository is private, and I did not re-run the scores.
Evidence
experiment notesgold-set testsnot re-run
05An agent can say "done" when nothing was tested.

A green check that is hard to fake

Problem
An agent can say "done" when nothing was tested. Early on, my gate printed ALL GREEN while four workspaces were untested.
What I did
I directed AI agents to build a verification gate for a game project. A full test run writes a green record tied to one commit and one clean working tree. Landing is refused without that record, and the landed tree must match the verified tree. A hook stops agents from writing into the record folder. I had the checks changed so they can fail.
Result
The procedure was one full verify per wave. A log of 45 push decisions (2 to 4 Oct) shows 18 holds, 8 passes on a green record, 1 refusal of a subagent push and 18 that went ahead after my yes.
Limit
The hook is not sandboxed. 13 waves landed since my last play test, so I added a human-only PLAYED step. The log does not show a green record for every wave.

06A brief says what to build, but rarely how to spot a wrong build.

Rule pages that list the wrong builds their tests must reject

Problem
A brief says what to build. It rarely says how to tell a wrong build from a right one.
What I did
In my game project, I directed AI agents to write one rule page per game rule. Each page says what correct looks like and which tests pin it down. It also names the likely wrong builds those tests must reject. A checker runs the pages inside every verify run.
Result
408 rule pages, 407 of them with tests, naming 572 wrong builds. A worker picks one page and knows what to build and how to check it. It works like a small test set for agents.
Limit
The tests belong to one game. The same project made 329 top-level documents, so the process outgrew the product.

Rules as code 07–11

07A rule written in a prompt is a rule a model can talk past.

Rules written as code that says no

Problem
A written rule is only a request. Under pressure, a model finds a way around it.
What I did
I moved my rules out of prompts and into the tool layer. On 1 Oct I directed six AI agents to build six plugins (mods) for Claude Code. They took 1 hour 48 minutes, and a seventh followed. A refusal is final: the agent reports it word for word and never works around it.
Result
7 mods, with about 9,300 lines of hook code and 8,200 lines of tests. In three days of logs the guards refused 22 memory-heavy jobs and 2 top-priced workers. For two guards, agents made dozens of deliberate breaks to see the tests catch them. 12 of my rules now have code behind them.
Limit
Mods are not sandboxed. The tool kit has no git history, and one deliberate break in a review round went uncaught.
Evidence
guard logsline countstests counted, not run
08Telling an agent not to touch my files does not stop it.

A kernel fence, not a polite request

Problem
A prompt that says "read only" is not a fence. An agent can still write files or read secrets.
What I did
I run risky agent jobs inside an operating-system fence. The system and home folders are read-only, credential folders are hidden and tokens are blanked. A time cap and a memory cap end runaway jobs. A short probe proves that writes and secret reads fail, and that allowed work still passes.
Result
The fence is 29 lines and the probe is 24; the probe passed 11 of 11. I reused the same recipe in four projects, including a 35-seat review panel and a hostile Codex audit.
Limit
An issue trigger built on the fence ran only in dry-run mode. The fence works on Linux only.
Evidence
probe resultsproject notesnot re-run
09A study tutor that hands out answers stops being a tutor.

The AI may teach, but I must produce, enforced in code

Problem
When I study with AI, it is easy to let it write the solution. Then I learn nothing.
What I did
In my study tools, plain code checks every tutor reply. It blocks extra code blocks, long code and any phrase from the real solution. I signed a pre-registered self-experiment to test the system. Build gates keep course material out of public builds, and they fail closed.
Result
The reply guard has 36 tests. A review found spacing tricks that slipped past it, so I had it hardened. A larger study tool has 1,458 tests in 33 files.
Limit
The self-experiment has no data yet. Most of the repositories are private, and nobody else has used the tools.
Evidence
test countsreview notescounted, not run
10An overnight run froze, and nobody noticed for hours.

Count the incident, build one small fix, arm it after a dry run

Problem
An overnight agent run froze. 21 workers waited on approval prompts for hours before anyone noticed.
What I did
I had my agents measure it: all 21 recursive deletes froze, and 22 worker calls stalled in all. The same day I directed five AI agents to build and test a small kit. Its guard hook fails open on its own bugs, and its away-switch expires after 16 hours. The memory watchdog started in log-only mode.
Result
In log-only mode the watchdog logged 54 would-stop lines for 4 jobs in one day, before any real kill was allowed.
Limit
The guard's first real use saw no stall and no block (3 log lines), so it is unproven. The watchdog is still log-only.
Evidence

11A worker's report can read like a yes.

Approvals an agent cannot give itself

Problem
A worker report can read like a yes. A tired owner might accept it.
What I did
I directed AI agents to build a small plugin layer for Claude Code. A decision closes only when my own typed reply (or one from my phone) holds the exact answer. It reads the origin stamp the tool engine gives each message. A worker report counts as data, never as approval. Plain code does the matching, no model.
Result
138 automated tests. 23 real decisions went through it over three days (2 to 4 Oct 2026).
Limit
Plugins are not sandboxed, so another plugin could still answer the confirm dialog. The spend-guard log has only a few real events.

Delegation at scale 12–17

12One agent at a time is slow; many at once collide.

One person, many workers, in measured waves

Problem
One agent at a time is slow. Many agents at once overwrite each other.
What I did
I directed AI agents to build in waves on one machine. Builders work on separate branches and files. One lead merges, as the only committer. In a private browser game-engine project I landed 49 merge waves in 8 days (26 Sep to 3 Oct). Peak was an estimated 20 workers on one day. From 18 Sep to 8 Oct I ran 82 scripted workflow runs with 1,941 agents. The biggest run had 331 agents and took 105 minutes.
Result
82 runs, 1,941 agents, 1,159 subagent spawns, 49 merge waves. The procedure was one full verify per wave. The 45-decision push log shows 8 landings on a green record.
Limit
These counts are volume, not quality. 13 waves landed since my last play test, which I wrote down as a gap.
Evidence
workflow logsgit historycounted, not re-run
13A worker with a loose brief edits files it should not touch.

Every job is a contract with a write scope

Problem
A worker with a loose brief edits things it should not touch.
What I did
For a private music studio project, every unit of work was a written contract: goal, files it may write, files it may not touch, and measurable acceptance lines. 172 contracts in 12 days. A script compared the git diff with the allowed files before the full test sweep ran. I directed AI agents to write the briefs, contracts and code.
Result
In about 27 hours over 10 and 11 Sep, 12 typed messages led to 16 contracted lanes merged. Tests passing rose from about 1,250 to 1,674 (1,113 three days earlier).
Limit
A UX audit had scored the product 3 of 10 while about 1,250 tests were green. Green tests were not enough. The repo is private, has no demo, and the human listening test has not run.
Evidence
contract filesgit historynot re-run
14A small open model fails on big, vague jobs.

Shrink the job until a small local model can win it

Problem
A small open model is cheap, but it fails on big, vague jobs. And "the model is weak" is not a number.
What I did
I directed AI agents to build a work loop for a 27B open model. A curator writes a ticket and one failing acceptance test. The small model, in a fresh session, edits only the source folder and never commits. The curator re-runs every gate and makes the only commit.
Result
28 tickets done in one day. 17 needed no repair prompt, 9 needed one and 2 needed two. There was 1 scope break. The full gate grew from 7 to 136 tests.
Limit
All commits fall on one day, with no licence and no automatic test runs. My records do not show who played the curator.
Evidence
workshop loggit historyper-ticket scorecards
15The model that builds a change is the worst judge of it.

Codex builds, Claude proves, a fresh reviewer blocks

Problem
The model that builds a change is the worst judge of it. I also wanted two vendors to work as one team.
What I did
I directed AI agents to build an eight-step branch pipeline. Codex builds. A Claude worker proves the build in memory-capped boxes. A fresh Codex session reviews, and the same builder fixes. The lead reads only the fix diff. A job queue gives each job its own list of files and never pushes.
Result
The queue is 1,808 lines with 142 test functions. Its first version drew 8 high and 4 medium review findings, fixed test-first. On 3 Oct I ran 114 headless Codex jobs in one day.
Limit
The tool kit is private and not under git, and the game project it served is closed. So there is no public demo.

16A worker that restarts forgets what it already tried.

A diary per task, three strikes, thinnest slice first

Problem
A resumed worker repeats the same failed attempt. Once, a loop ran 87 laps with no product progress.
What I did
Every worker writes one line per attempt to a diary and reads it first when resumed. The third identical failure forces a new approach, and the sixth ends the task. Each job builds the thinnest end-to-end slice first. Claude and Codex workers share the same rules.
Result
341 diaries in four days, with 11,758 lines and 340 failure lines. A worker costs about 35,000 tokens just to start, so a short diary is cheap insurance.
Limit
I found no test for the diary script, and the benefit is not measured. The diary folder grew to 1.2 GB.
Evidence
diary filesline countsbenefit not measured
17If the most expensive model does every job, the cost climbs.

A written ladder of workers, priced

Problem
If the most expensive model does every job, the cost climbs and the lead's context fills up.
What I did
Spend rules were in writing from 18 Sep. The full ladder came on 1 Oct: six levels (lead, hard work, review, routine, search, second-opinion model) with price ratios (list prices, checked 1 Oct), tiny-job limits, a move-up rule after two failed tries, and a prompt gate that stops top-priced workers unless I say yes. I directed AI agents to build the agent files and the guard.
Result
Sonnet 5.5 became the routine worker on 29 Sep. In the 4-day part week to 8 Oct it did 69% of worker turns, or about 57% without one 96-agent review run. 693 of 1,159 subagent spawns used the three ladder levels; 50 used levels outside the ladder.
Limit
I cannot show the ladder caused the shift. The table recorded practice that had already started. Whether the lead or the workers cost more is still open.

Owner in control 18–21

18Agents can quietly rewrite the rules they are meant to follow.

A rulebook that updates itself, only from my words

Problem
Rules for agents drift. A web page or a worker report could slip in a new rule.
What I did
My working rules live in one file that saves every version and checks itself against a 10,000-byte cap. It changes only from what I type. Text in files, web pages or reports never edits a rule. Rules that keep coming back then become code.
Result
40 saved versions, from 1,045 bytes to 9,996. 10 failures in the log each produced a rule, and 12 rules now have code behind them.
Limit
The memory index links to 13 notes that no longer exist. A long rules file also costs tokens, which is why I capped it.
Evidence
version historyrule tablescounted
19A good idea fades if building it takes weeks.

From a dictated idea to a checked thing on a real device in hours

Problem
Speed alone proves little. But a good idea fades if building it takes weeks.
What I did
I dictate the idea, the lead briefs workers, and the result is checked where it will run. Each fast case ends in a read-back check or a real test on my phone.
Result
An iPhone app went from empty project to all five phases in about 4 hours. I checked it on a real phone the next day. A small power-settings app took 17.5 minutes from request to commit, with 29 of 29 read-back checks.
Limit
Nothing here is public, and no outside user has used it. The times come from commits and transcripts, and self-timing is weak proof.

20With many agents running, I felt I was losing control.

A control panel for an owner who writes no code

Problem
With many agents running, decisions piled up. I did not want to be the human who just says yes.
What I did
I keep taste and every hard-to-undo choice, and I directed AI agents to build the surface for it. Each decision comes with two or three options, a recommendation and exact reply words. A plain-language score checks the reports. Explainer pages end with check questions. In the game project, only I could tick the PLAYED box.
Result
23 decisions went through the answer pane in three days. The writing scorer has 27 tests. The PLAYED step came after 13 waves had landed with no play test.
Limit
More than once, I lifted my own stop line late at night. The explainer pages are not scored by anyone else.

decision logsexplainer filescounted
21Models change every few months, so what in a project should last?

Keep what no model can rebuild; let the rest be thrown away

Problem
Models get better every few months. Much of what an agent writes today, a better one will redo.
What I did
In a new game project I split everything into two kinds. Truth is my words, my rulings and dated records, and it is add-only. Everything else is derived, and a stronger model can rebuild it. Ten written laws hold the split, and a checker enforces what a machine can.
Result
24.5 hours from dictated idea to last commit, with six playable scenes. 95 rulings, each with my exact quote. Hostile critic agents broke the checker in 10 of 21 cases, and three fix rounds followed.
Limit
No stranger has played anything, and 12 of 12 assumptions are untested. Nothing has been committed since 4 Oct.

Measure, cost and honesty 22–25

22A number without its baseline looks better than it is.

Numbers beside their baseline, failures beside their wins

Problem
Agents report what went well. A number with no baseline looks better than it is.
What I did
From day two I asked for status as actually built, not as planned. My projects keep failure logs, honest null results and "not checked" lists. My global rule: show any model accuracy beside the "always guess the most common answer" baseline.
Result
One edit router scored 0.942. The baseline scored 0.234, and a keyword rule 0.830. A research check on 5 Oct found 4 of 7 blog numbers wrong. A review of my own portfolio passed 0 of 21 repositories on a recruiter check.
Limit
Several repositories are private. My weakest results, like a trial with no data and no users yet, stay written as they are.

23A runaway agent loop can spend real money overnight.

Spend as code: reserve first, stop for good

Problem
A runaway loop can spend real money while I sleep. Once, a "free" test run billed a paid API by mistake.
What I did
Every paid call runs under a ledger. A gate writes the worst-case charge before the call leaves. An unknown outcome keeps the full charge. An overspend sets a stop latch that never clears. Subscription lanes strip metered keys, so nothing bills silently.
Result
One night run stopped at its $5 balance floor, as designed. A later run used $1.34 of a $5 cap. A research batch settled 180 calls with 0 unknown, $0.93 of a $6 ceiling.
Limit
The ledgers show the metered share, not the total cost. An earlier spend harness had no automatic tests and caused a defect.
Evidence
spend ledgersrun logsmetered share only
24Tools and process pile up, and some stop paying for themselves.

Test before adding, delete what does not pay

Problem
Tools and process pile up. Each one costs attention, and some stop paying for themselves.
What I did
I test a tool before I adopt it, and I delete what stops earning its place. That includes seats, scripts, process pages and even a finished portfolio site. I archive first, with a checksum or an undo list, so a cut is safe.
Result
On 25 Sep I removed an old worker scheme of 219 files, after a checksummed archive. About 250 orchestrator tools came down to the 3 I kept. One protocol shrank from 370 lines to 138.
Limit
Pruning cost me once. A tidy-up removed my live context plugin, and context doubled for about two days.

25A long session re-reads its whole context on every turn.

Measure the context policy, cut what does not pay

Problem
A long agent session re-reads its own context on every turn. That is most of the cost.
What I did
I extended an open-source (MIT) compaction plugin for Claude Code and replayed my own recorded sessions through it. The small decision model it used picked no better than a free rule, so I removed it. I kept the one lever that paid: when to compact. A simulation over 204 sessions (assumed prices, stated) chose the trigger. Directed AI agents wrote and reviewed the code.
Result
Replay of 3 sessions (14 points): 24.2% of characters removed by the small model, 24.1% by the free rule, 75 regrets each. Mean context per reply: 353k tokens with no plugin, 152k with the early plugin versions, about 135k with version 0.4.0.
Limit
A replay and a simulation, not a controlled trial. The context drop is a before-and-after, not a test, and most of it came with the trigger the plugin already had. I re-tuned that trigger.

How I work

Principles

Seven rules I keep when I work with agents. Open one to see how I use it.

Work flows down. Short reports flow up.

I write the brief, and the lead hands each job to the cheapest worker that can do it well. The worker writes its full report to a file and replies in 15 lines or fewer. That keeps the lead's context small, and context is most of the cost. The priced ladder came in phase P6 (idea 17).

A report is data, never approval.

A worker report can read like a yes, but only my own typed reply closes a decision. Plain code checks where each message came from, so no agent can approve its own work. In three days, 23 real decisions went through this check (idea 11).

A real check before "done".

An agent says "done" easily, so for me done means a check that ran on the change itself. For code, that is the tests, the type-checker or the build. In my game project, landing was refused without a green record from a full test run (idea 05).

A check is not a guard until it has failed.

If a check has never failed, I cannot tell whether it tests anything. So I have agents break things on purpose and watch the check go red. Once my gate printed ALL GREEN while four workspaces were never tested. In one sweep, 2 of 16 guards did not notice a deliberate break (idea 01).

A number needs its baseline.

A score means little until I see what a simple rule gets. So every model accuracy I report sits beside the "always guess the most common answer" baseline. My context plugin's small model did no better than a free rule, so I removed it (idea 25).

Rules that keep coming back become code.

When I repeat a rule to agents, I move it out of the prompt and into a hook. A hook refuses in the tool layer, where a model cannot talk its way past it. In phase P6, six agents built six such mods in under two hours (idea 07). Today 12 of my rules have code behind them.

Measure, then cut what does not pay.

I test a tool before I adopt it, and I delete what stops earning its place. I archive first, with a checksum or an undo list, so a cut is safe. In phase P2 my hand-run fleet cost more than it paid, so I deleted it (idea 24).

Honest limits

What this page does not show

Seven limits, in my own words. Open one to see which project it touches and what would close the gap.

My repositories are private, so you cannot run the code yourself.

My game project and the music studio live in private repositories, like most of my work. My skills chart marks public, runnable proof as missing. To close it, I need one small public tool with tests, like the rule pages of idea 06.

Counts of agents, commits and waves show volume, not quality.

In the music studio project, about 1,250 tests were green. Yet a UX audit scored the product 3 of 10 (idea 13). To show quality, I need human tests and outside users.

I counted tests from git and logs; I did not re-run every suite.

The audit counted tests and read their logs; it did not run them again. So the 142 test functions of my job queue show effort, not a pass today (idea 15). To close the gap, I need a clean re-run with a dated result for each project I show.

AI agents wrote the code; I directed them and wrote none of it.

I write the specs, set the checks and decide what ships; the agents type the code. To steer without coding, I directed agents to build the control panel in idea 20. My skills chart still marks "explaining the code that ships" as partial, so I need to close that gap.

I have no outside players or paying users yet.

13 waves in my game project landed with no play test, so I added a PLAYED box (idea 05). No stranger has played my newest game either (idea 21). To close this gap, I need a small public release and real players.

My cost figures are list-price estimates, not invoices.

Token counts come from logs, but the dollar figures use list prices, and two sources did not agree. So the worker ladder in idea 17 compares price ratios, not real bills. To close the gap, I need the cost per finished task from real invoices.

I make no claim that these ideas are new.

The audit compared my ideas only with the research it read. I did not survey other people's systems, so someone else could already do the same thing. To claim novelty, I would need a real survey, and this page is not one.
