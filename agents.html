I direct AI agents,
and I adapt
as they get better.

For 107 days I worked with AI coding agents, almost every day. I did not build the gates, guards and tests myself: I asked the agents to check their own work, and with every better model version they did more of it on their own. My part was to notice each change and adapt my workflow to it. This page is the result of a large-scale audit of my entire work with AI agents. I made it by deploying a large agent workflow across my whole portfolio, on GitHub and on my computer.

Checks that can fail 01–06

01A check that never failed gives no proof that it tests anything.

A check is not a guard until I have watched it fail

Problem
A check that has never failed prints OK, and everyone trusts it.
What I did
From July, a worker had to revert its own change and see its check go red. Agents broke guards on purpose, then audited the breaking tool too. A gate that did not run now exits with an error instead of printing OK.
Result
In one session, 2 of 16 guards did not notice a deliberate break. The breaking tool once scored 100% while testing nothing, until a baseline check fixed it. The habit recurs across several projects.
Limit
Counts come from notes and git history; I did not re-run the suites.
Evidence

02A worker's finding can sound right and still be wrong.

A second stage whose only job is to refute

Problem
Some confident findings are wrong, and acting on one wastes a day.
What I did
I directed AI agents to add a stage that tries to refute each claim. It re-opens every cited file, re-runs the check or argues the opposite. Every report ends with a list of what was not checked.
Result
In a 35-seat review run on a game project, the verifier refuted 6 of 203 findings, about 3%. In my portfolio review, a check settled most of 11 facts that differed between reports.
Limit
The verifier is a model, often from the finder's family, so both can share blind spots. A low refutation rate is not a quality score.
Evidence
panel recordsreview plansmodel-made counts
03Two reviewers from one model family can share the same blind spots.

A reviewer from another model family, for important changes

Problem
Two sessions from the same model family can miss the same faults. Their agreement is not an independent review.
What I did
From 7 Aug, important changes get a second opinion from a different model family, such as Codex or Kimi. My rule: no two reviewers from the same family in the same role. I directed AI agents to run the reviews.
Result
In one frozen 11-file snapshot, two outside reviewers shared only 1 of 11 findings. So I stopped treating one reviewer as independent.
Limit
That is one example, not a general rate. Routine diffs still get a Claude reviewer. A model reviewer is not a human reviewer.
Evidence
review reportsproject notesone example
04A model judge can give two verdicts on the same answer.

Measure the judge before I trust the score

Problem
If the judge is noisy, a small change in the score is noise too.
What I did
I gave my own AI grader identical answer pairs and counted the flipped verdicts.
Result
First test: 2 of 17 rows flipped. Three graders on 18 more rows showed no flips, so about 6% pooled (2 of 35). I corrected my first claim of 11% the same day. A one-row change now counts as noise.
Limit
The legal-text assistant I measured this on missed its target: 43% defensible answers against 75 to 80%. The repository is private, and I did not re-run the scores.
Evidence
experiment notesown correctionnot re-run
05An agent can say "done" when nothing was tested.

A green check that is hard to fake

Problem
On 19 Sep my own gate printed ALL GREEN while four workspaces were untested.
What I did
I directed AI agents to build a verification gate for a game project. A full test run writes a green record tied to one commit. Landing is refused without that record. A hook stops agents from writing into the record folder.
Result
A log of 45 push decisions over three days shows 18 holds, 8 passes on a green record, 1 refusal and 18 that went ahead after my yes.
Limit
The hook is not sandboxed. 13 waves landed before anyone played the game, so I added a play-test sign-off.
Evidence
git historyhook logscounted, not re-run
06A brief says what to build, but rarely how to spot a wrong build.

Rule pages that list the wrong builds their tests must reject

Problem
A brief rarely says how to tell a wrong build from a right one.
What I did
From 28 Sep, I directed AI agents to write one rule page per game rule. Each page says what correct looks like, which tests pin it down and which likely wrong builds those tests must reject. A checker runs the pages in every verify run.
Result
408 rule pages, 407 with tests, naming 572 wrong builds. The pages are built to work like a small test set.
Limit
The tests belong to one game. The same project made 329 top-level documents, so the process outgrew the product.
Evidence
rule-page filesgit historycounted, not re-run

Rules as code 07–11

07A rule written in a prompt is a rule a model can talk past.

Rules written as code that says no

Problem
Under pressure, a model can find a way around a written rule.
What I did
I moved key rules into the tool layer. I directed AI agents to build six plugins (mods) for Claude Code in one evening, and a seventh the next day. Three are guards; the rest are panes and helpers. A refusal is final.
Result
About 500 test cases, counted, not run for this page. In a small live log, the spend guard refused 2 top-priced workers. 11 of my rules now have code behind them.
Limit
Mods are not sandboxed, so a guard is hard to talk past, not impossible. The kit has no git history.
Evidence
guard logstest countscounted, not run
08Telling an agent not to touch my files does not stop it.

A kernel fence, not a polite request

Problem
A prompt that says "read only" does not stop an agent writing files or reading secrets.
What I did
I directed AI agents to build a small Linux sandbox for risky agent runs. System and home are read-only, credential locations are unreachable and tokens are blanked. Time and memory caps end runaway jobs. A probe checks that writes and secret reads fail, and that normal work passes.
Result
The probe's 11 checks passed. I reused the recipe on a security audit seat and on a 35-reviewer panel for a game project.
Limit
Sandboxing is a known pattern, and this one works on Linux only. A trigger built on it ran in dry-run only.
Evidence
probe resultsproject notesnot re-run
09A study tutor that hands out answers stops being a tutor.

The AI may teach, but not hand over the answer

Problem
If the AI writes the solution, I learn nothing.
What I did
I directed AI agents to build a study tutor. Plain code checks every reply and rejects extra code blocks, long code or any phrase from the real solution. Prompt rules cover what the code cannot catch.
Result
The reply check has 36 tests. A review found spacing tricks that slipped past it, so I had it hardened. I signed a pre-registered design for a one-person experiment.
Limit
The check is a heuristic and cannot catch an answer in plain prose. The experiment has no data yet. Nobody else uses the tools.
Evidence
test countsreview notesno data yet
10An overnight run froze, and nobody noticed for hours.

Count the incident, build one small fix, arm it after a dry run

Problem
In a large overnight run, 21 workers waited on approval prompts for hours.
What I did
Agents measured it from the logs: 23 of about 6,078 worker shell calls got no answer. The same day I directed five AI agents to build a small kit. Its guard fails open on its own bugs; its away-switch expires after 16 hours.
Result
The memory watchdog started in log-only mode. It wrote 54 would-stop log entries in one day before any real kill was allowed.
Limit
The guard's first real use saw no stall and no block (3 log lines), so it is unproven. The watchdog is still log-only.
Evidence
incident logtool logscounted, not re-run
11A worker's report can read like a yes.

Approvals an agent cannot give itself

Problem
A worker report can read like a yes. A tired owner might accept it.
What I did
I directed AI agents to build a small plugin layer for Claude Code. A decision closes only when my own typed reply, or one from my phone, holds the exact answer. It uses the origin stamp the tool engine gives each message. A worker report is data, never approval. Plain code does the matching.
Result
138 automated tests. 23 real decisions went through it over three days (2 to 4 Oct 2026).
Limit
Plugins are not sandboxed, so another plugin could still answer the confirm dialog. The spend-guard log has only a few real events.
Evidence
test countsdecision logscounted, not re-run

Delegation at scale 12–17

12One agent at a time is slow; many at once collide.

One person, many workers, in measured waves

Problem
Many agents at once overwrite each other.
What I did
I directed AI agents to build in waves on one machine. Builders work on separate branches and files. One lead merges, as the only committer, and one full check runs per wave.
Result
In a private browser game-engine project, 49 merge waves landed in 8 days (26 Sep to 3 Oct), with a peak of about 20 workers on one day. From 18 Sep to 8 Oct I ran 82 scripted workflow runs with 1,941 agents; the biggest had 331.
Limit
These counts are volume, not quality. 13 waves landed before anyone played the game. Only I can judge if it is fun.
Evidence
workflow logsgit historycounted, not re-run
13A worker with a loose brief edits files it should not touch.

Every job is a contract with a write scope

Problem
A loose brief lets a worker edit the wrong files.
What I did
In a private music studio project, every unit of work was a written contract: goal, files it may and may not touch, and measurable acceptance lines. A script checked the git diff against the allowed files. AI agents wrote the briefs, contracts and code.
Result
172 contracts in 12 days. In one day, 12 typed messages led to 17 contracted lanes integrated, and passing tests rose from about 1,110 to 1,674.
Limit
An outside-family AI audit scored usability 3 of 10 while over 1,200 tests were green. The repository is private, and the human listening test has not run.
Evidence
contract filesgit historynot re-run
14A small open model fails on big, vague jobs.

Shrink the job until a small local model can win it

Problem
A small open model fails on big, vague jobs.
What I did
I designed a loop with AI agents. A curator agent writes a ticket and one failing test. A local 27B open model implements it, with no commit rights. The curator re-runs every check and makes the only commit.
Result
In one day, 28 tickets built a 136-test workflow runner. 17 needed no repair prompt, 9 needed one and 2 needed two. 1 scope break, a blocked edit done through a shell command, was closed.
Limit
A one-day build, with no automatic test runs. My records do not show which model played the curator.
Evidence
workshop loggit historyper-ticket scorecards
15The model that builds a change is a weak judge of it.

Codex builds, Claude checks, a fresh reviewer blocks

Problem
I wanted two vendors to work as one team, and neither to judge its own work.
What I did
I directed AI agents to build an eight-step branch pipeline. Codex builds. A Claude worker checks the build in memory-capped boxes. A fresh Codex session reviews, and the same builder fixes. The job queue itself never pushes.
Result
The queue has 142 test functions. Its first review found 8 high and 4 medium issues, fixed with tests. On 3 Oct about 114 headless Codex jobs ran, by my sorting of the logs.
Limit
The kit is private and not under git, and the game project it served is closed. There is no public demo.

16A worker that restarts forgets what it already tried.

A diary per task, three strikes, thinnest slice first

Problem
A resumed worker repeats the same failed attempt. Once, a loop ran 87 laps with no product progress.
What I did
I wrote four rules for my AI workers. Each keeps a one-line-per-attempt diary and reads it first when resumed. After three identical failures it must change approach; after six it stops and reports. Each job builds the thinnest end-to-end slice first. AI agents built the helper script.
Result
About 340 diaries with 11,758 lines in the first days of use. Claude and Codex workers share the same rules.
Limit
The helper script has no test yet. The diaries prove use, not benefit, and I have not measured the benefit.
Evidence
diary filesline countsbenefit not measured
17If the most expensive model does every job, the cost climbs.

A written ladder of workers, priced

Problem
Using the top model for every job costs too much.
What I did
On 1 Oct my written spend rules became a ladder of six worker levels, with price ratios, tiny-job limits and a move-up rule. A prompt gate stops top-priced workers unless I say yes. I directed AI agents to build the gate.
Result
The cheaper Sonnet model became the routine worker on 29 Sep. Nine days later it did 69% of worker turns in a partial week. 50 of 1,159 spawns used levels outside the ladder.
Limit
The shift matches the policy, but I cannot show the policy caused it. Whether the lead or the workers cost more is still open.
Evidence
transcript aggregatesguard logslist-price assumptions

Owner in control 18–21

18Agents can quietly rewrite the rules they are meant to follow.

A rulebook that keeps its history

Problem
A web page or worker report could slip in a new rule.
What I did
My working rules live in one file. An agent keeps it current. I directed AI agents to build a hook that checks every edit, saves every version, holds a 10,000-byte cap, protects four safety lines and can undo. The file says only my own typed words change a rule.
Result
40 saved versions, from 1,045 bytes to 9,996. 10 logged failures each produced a rule; 11 rules now have code behind them.
Limit
The words-only rule is written and protected, not checked by code. A few of my other notes still have broken links.

From a dictated idea to a checked result in hours

A good idea fades if building it takes weeks.
What I did
I dictate the idea, and AI agents build it. Each fast case ends in a check where it will run, or in a written list of what was not tested.

20With many agents running, I felt I was losing control.

A control panel for an owner who writes no code

Problem
I did not want to be the human who just says yes.
What I did
I keep taste and irreversible choices. I directed AI agents to build the surface for it: a decision form with options, a recommendation and exact reply words; a plain-language writing score; explainer pages with check questions; and a play-test sign-off that only my own typed reply can fill.
Result
23 real decisions went through it in three days (2 to 4 Oct), covered by 138 automated tests.
Limit
The pages are disposable and nobody else scores them. The file guard is best effort. On 2 to 3 Oct I lifted my own stop line for a night run.

21Models change every few months, so what in a project should last?

Keep what no model can rebuild; let the rest be thrown away

Problem
A better model will redo much of what an agent writes today.
What I did
In a browser game prototype I split everything in two. Truth is my words and dated decisions, add-only. The rest is derived, and a stronger model can rebuild it. Ten written laws guide agents. I directed AI agents to build a script that checks what a machine can.
Result
In 24.5 hours: six playable scenes and 95 rulings. A Codex critic found 10 wrong results in 21 hostile tests, fixed over three rounds.

A git history rewrite can hide old versions. No outside player has tried it, and it is paused.

Measure, cost and honesty 22–25

22A number without its baseline looks better than it is.

Numbers beside their baseline, failures beside their wins

Problem
A number with no baseline looks better than it is.
What I did
From my first week I asked for status as built, not as planned. My notes keep failure logs and "not checked" lists. One rule covers every project: show model accuracy beside the "always guess the most common answer" baseline.
Result
A small model beat a keyword rule on one task (0.94 against 0.83, baseline 0.23) and lost on another, so I cut it back. In an AI audit of my portfolio, 0 of 21 repositories passed a recruiter check.
Limit
My repositories are private, I am the only user, and agents did most of the writing and grading.

23A runaway agent loop can spend real money overnight.

Spend as code: reserve first, stop for good

Problem
Once, a "free" test run billed a paid account by mistake.
What I did
I directed AI agents to build a spending gate. Before any paid model call, it writes the worst-case charge to a ledger. If the result is unknown, the full charge stays. If real usage passes the reserve, a stop latch trips, and nothing clears it.
Result
In one research batch, 180 settled calls cost $0.93 inside a $6 ceiling, with 0 unknown. A night run stopped at its $5 floor, as designed.
Limit
The ledgers show the metered share, not the total cost. A harness defect let some jobs spend their budget and return nothing; I replaced it.
Evidence
spend ledgersrun logsmetered share only
24Tools and process pile up, and some stop paying for themselves.

Test before adding, delete what does not pay

Problem
Each tool or process costs attention, and some stop paying.
What I did
I review a tool before I adopt it, and I cut what stops earning its place: worker setups, scripts, process pages, even my old portfolio site. AI agents make the cuts on my approval. They archive first, with a checksum or an undo list, so a cut is safe.
Result
On 25 Sep agents removed an old worker scheme of 219 files, after a checksummed archive. I reviewed about 250 listed orchestrator tools against a plain instruction.
Limit
Pruning cost me once. A tidy-up moved my live context plugin to the trash, and context doubled for about two days.
Evidence
git historyarchive manifestscounted
25A long session re-reads its whole context on every turn.

Measure the context policy, cut what does not pay

Problem
Re-reading context each turn was two thirds of the cost in one session I measured.
What I did
I copied an open-source (MIT) compaction plugin for Claude Code and replayed my own sessions through it. Its small decision model did no better than a free rule, so I removed it. A simulation of 204 sessions chose the trigger. AI agents built and reviewed the code.
Result
In a replay of 3 sessions, model and rule removed 24.2% and 24.1%. Mean context per reply fell from about 353k tokens to about 134k.
Limit
Replays and a simulation, not a controlled trial. The drop is a before-and-after over different weeks.

How I work

Principles

Seven rules I keep when I work with agents. Open one to see how I use it.

Work flows down. Short reports flow up.

I write the brief, and the lead hands each job to the cheapest worker that can do it well. The worker writes its full report to a file and replies in 15 lines or fewer. That keeps the lead's context small, and context is most of the cost. The priced ladder came in phase P6 (idea 17).

A report is data, never approval.

A worker report can read like a yes, but only my own typed reply closes a decision. Plain code checks where each message came from, so no agent can approve its own work. In three days, 23 real decisions went through this check (idea 11).

A real check before "done".

An agent says "done" easily, so for me done means a check that ran on the change itself. For code, that is the tests, the type-checker or the build. In my game project, landing was refused without a green record from a full test run (idea 05).

A check is not a guard until it has failed.

If a check has never failed, I cannot tell whether it tests anything. So I have agents break things on purpose and watch the check go red. Once my gate printed ALL GREEN while four workspaces were never tested. In one sweep, 2 of 16 guards did not notice a deliberate break (idea 01).

A number needs its baseline.

A score means little until I see what a simple rule gets. So every model accuracy I report sits beside the "always guess the most common answer" baseline. My context plugin's small model did no better than a free rule, so I removed it (idea 25).

Rules that keep coming back become code.

When I repeat a rule to agents, I move it out of the prompt and into a hook. A hook refuses in the tool layer, where a model cannot talk its way past it. In phase P6, six agents built six such mods in under two hours (idea 07). Today 12 of my rules have code behind them.

Measure, then cut what does not pay.

I review a tool before I adopt it, and I cut what stops earning its place. I archive first, with a checksum or an undo list, so a cut is safe. In phase P2 my hand-run fleet cost more than it paid, so I deleted it (idea 24).

Honest limits

What this page does not show

Seven limits, in my own words. Open one to see which project it touches and what would close the gap.

My repositories are private, so you cannot run the code yourself.

My game project and the music studio live in private repositories, like most of my work. My skills chart marks public, runnable proof as missing. To close it, I need one small public tool with tests, like the rule pages of idea 06.

Counts of agents, commits and waves show volume, not quality.

In the music studio project, over 1,200 tests were green. Yet an AI audit from another model family scored the product 3 of 10 (idea 13). To show quality, I need human tests and outside users.

I counted tests from git and logs; I did not re-run every suite.

The audit counted tests and read their logs; it did not run them again. So the 142 test functions of my job queue show effort, not a pass today (idea 15). To close the gap, I need a clean re-run with a dated result for each project I show.

AI agents wrote the code; I directed them and wrote none of it.

I write the specs, set the checks and decide what ships; the agents type the code. To steer without coding, I directed agents to build the control panel in idea 20. My skills chart still marks "explaining the code that ships" as partial, so I need to close that gap.

I have no outside players or paying users yet.

13 waves in my game project landed with no play test, so I added a PLAYED box (idea 05). No stranger has played my newest game either (idea 21). To close this gap, I need a small public release and real players.

My cost figures are list-price estimates, not invoices.

Token counts come from logs, but the dollar figures use list prices, and two sources did not agree. So the worker ladder in idea 17 compares price ratios, not real bills. To close the gap, I need the cost per finished task from real invoices.

I make no claim that these ideas are new.

The audit compared my ideas only with the research it read. I did not survey other people's systems, so someone else could already do the same thing. To claim novelty, I would need a real survey, and this page is not one.
